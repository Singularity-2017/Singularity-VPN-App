# ADR 0001 — Адрес control plane переживает сборку

- Статус: предложено
- Дата: 2026-10-28

## Контекст

Адрес control plane вшит в бинарник
(`buildinfo.Control_plane`, `internal/buildinfo/buildinfo.go:14`) и читается
напрямую в четырёх местах:

- `cmd/svpn-service/service_windows.go:450` — клиент API (`api.New`);
- `cmd/svpn-service/service_windows.go:541` — снимок сетевого окружения
  (`winplatform.Capture_network`);
- `cmd/svpn-service/update_windows.go:44` — канал обновлений через control plane;
- `cmd/singularityvpn/portal.go:14` — ссылка на личный кабинет в окне.

`api.Client` держит один `base_url` всю жизнь
(`internal/api/control_plane.go:29`). Когда control plane переезжает —
хостер меняет адрес или мы переносим его сами, как 2026-10-16, — каждая
установленная копия продолжает звонить на старый адрес. Обновление тоже не
спасает, пока манифест сначала берётся с того же адреса.

Что уже есть и не зависит от адреса control plane:

- Подписанный манифест выпуска (`internal/update/manifest.go:36`), Ed25519,
  проверяется ключами, вшитыми в сборку (`update.Trusted_keys`); приватный
  ключ есть только на машине сборки.
- Каналы, не зависящие от control plane: зеркала из последнего проверенного
  манифеста (`State.Mirrors`, `internal/update/updater.go:233`) и вшитое
  запасное зеркало на хостинге кода (`buildinfo.Update_mirror`).
- Защита от повтора: `State.Highest_version`; для одной версии побеждает
  более поздний `released_at` (`internal/update/updater.go:223`).
- Незнакомые поля манифеста игнорируются (`manifest.go`, `Parse`), так что
  новое поле безвредно доходит до старых сборок.
- Проверка идёт раз в шесть часов (`Check_interval`, `updater.go:93`).

На стороне сервера ноды уже знают текущий адрес control plane
(`/etc/singularity/control-addr`), но клиентам его не отдают.

## Что на кону

Приложение отправляет control plane токен (Bearer). Тот, кого приложение
считает control plane, получает этот токен и может действовать от имени
пользователя, а ещё решает, через какие ноды и профили пользователь
подключается.

## Модель угроз

Противники, против которых решение должно устоять:

1. **Новый хозяин старого адреса.** Хостер переадресовал наш сервер и
   позже отдал старый IP другому клиенту. Каждая копия, которая всё ещё
   знает только его, шлёт туда токен. Эту угрозу сценарий переезда создаёт
   сам, без усилий со стороны нападающего.
2. **Подделыватель «control теперь там».** Любой, кто может ответить на
   один из запросов приложения — зеркало, нода, captive portal, коробка
   цензора, — пытается перенаправить приложение на свой адрес.
3. **Повторитель.** Кто-то подаёт старое, честно подписанное утверждение
   с адресом, от которого мы уже отказались (дальше это угроза 1).

Явно вне рамок, и сказано это, чтобы не обещать лишнего:

- **Наблюдатель на пути к текущему control plane.** Боевой control plane
  доступен по обычному `http` (`local/app.env`), поэтому токен уже идёт по
  сети открытым текстом в каждом запросе. Ни один вариант из этого ADR не
  делает это ни лучше, ни хуже. Перевод control plane на TLS с сертификатом,
  закреплённым в приложении, — отдельное решение, отмеченное в
  «Последствиях»; из двух рисков он больший.
- Компрометация ключа подписи на машине сборки: она уже позволяет выпустить
  любой код, так что доверие ей в вопросе адреса ничего не добавляет.

Требование, которое отсюда следует: **адрес принимается только из
утверждения, подписанного вшитым в сборку ключом и более нового, чем то,
из которого взят текущий адрес; адрес, который более новое утверждение
убрало, больше никогда не используется.**

## Варианты

1. **Адреса control plane в подписанном манифесте.** Новое поле манифеста
   перечисляет базовые URL control plane. Доверие то же, что у обновлений;
   манифест доступен через зеркала и хостинг кода без control plane.
   Цена: после переезда владелец заново публикует манифест
   (`deploy.exe app-release`); клиенты подхватывают его в течение шести
   часов или сразу, если control plane перестал отвечать (см. «Решение»).
2. **Спросить ноду из последних профилей.** Работает само, но ответ ноды
   ничем не подтверждён. Чтобы это стало безопасным, нужен ключ
   идентичности control plane, закреплённый в приложении, подпись
   control plane на собственном адресе этим ключом, ноды, которые передают
   эту подписанную запись, и HTTP-точка для клиентов на каждой ноде,
   которой у нод нет. Изменения в двух репозиториях и на каждой ноде.
3. **Ноды проксируют `/vpn/api/` на control plane.** Любая нода становится
   входом в API, что заодно помогает, когда адрес control plane заблокирован
   из России. Самое дорогое: прокси на каждой ноде, а без сквозного TLS
   каждая нода читает каждый токен, что расширяет угрозу 2, а не закрывает её.

DNS-имя не рассматривается: владелец против зависимости от внешнего сервиса.

## Решение

**Вариант 1.** Только он выполняет требование ключами и каналами, которые у
приложения уже есть, и только он делается целиком в приложении плюс
небольшая правка инструмента выпуска.

Подробности:

- **Поле.** `control_planes: [base URL, ...]` в манифесте, не больше 4,
  каждый — абсолютный URL `http`/`https` без query, fragment и user info.
  `http` разрешён только потому, что боевой сервер сегодня на `http`;
  когда control plane перейдёт на TLS, выпуск, который закрепит
  сертификат, сузит это до `https`.
- **Свежесть.** Сохранённый список помнит `released_at` манифеста, из
  которого он взят. Манифест заменяет список, только если его
  `released_at` строго позже. Манифест без поля ничего не меняет (пустой
  список — не «control plane нет»). Это закрывает угрозу 3: старый манифест
  не вернёт адрес, который убрал более новый.
- **Без возврата к вшитому адресу.** Когда подписанный список сохранён,
  вшитый адрес больше не используется — возврат к нему и есть угроза 1.
  Вшитый адрес — только первое значение, пока ничего не сохранено.
- **Где хранится.** Один файл, `control-plane.json` в закрытом каталоге
  данных службы (`%ProgramData%\Singularity VPN`, запись только у
  LocalSystem и Administrators, как у `update\state.json`). Пишется
  атомарно. Файл, которого нет или который не разбирается, значит «ничего
  не сохранено» и пишется в лог; он никогда не значит «control plane нет».
- **Чей он.** Небольшой пакет (`internal/control_address`) отвечает за
  `Load`, `Current`, `Offer(list, released_at)` и оповещение об изменении.
  Updater вызывает `Offer` после проверки манифеста; клиент API, снимок
  сети и собственный канал обновлений через control plane читают
  `Current`. Окно получает адрес для ссылки на кабинет от службы по IPC, а
  не из `buildinfo`.
- **Смена на ходу.** `api.Client` берёт базовый URL на каждый запрос из
  источника, а не из зафиксированной строки, так что смена действует без
  перезапуска службы. При нескольких адресах запросы идут на первый; тот,
  что ответил последним, встаёт вперёд. Это переключение между адресами,
  которые мы подписали, а не поиск.
- **Быстрее шести часов.** Когда control plane не ответил N попыток
  подряд (предложение: 3, с промежутком не меньше 10 минут), служба просит
  updater проверить раньше срока, только по зеркалам. Не чаще раза в час,
  чтобы сбой не долбил зеркала.
- **Журнал.** Смена адреса — строка журнала по-русски
  («Сервер управления переехал, адрес обновлён из подписанного манифеста»),
  без самого адреса.

## Последствия

- Переезд больше не бросает установленные копии, если владелец заново
  опубликовал манифест; хотя бы одно зеркало или хостинг кода должны быть
  доступны.
- Копия, которая пропустила окно между переездом и повторной выдачей
  старого IP, защищена всё равно: сохранив подписанный список, она уже не
  вернётся к вшитому адресу; до этого вшитый адрес — единственный, который
  у неё когда-либо был, так что по сравнению с сегодняшним днём ничего не
  теряется.
- У владельца ручной шаг при каждом переезде. `deploy.exe migrate` должен
  его напомнить.
- Копии, собранные до этого изменения, поле игнорируют и остаются на
  старом адресе; их спасает только обновление, и само обновление доходит
  до них через зеркала.
- **Здесь не решено:** токен открытым текстом по `http`; адрес control
  plane, заблокированный из России. Для второго путь — вариант 3 или
  вариант 2 с закреплённым ключом идентичности; для первого — TLS с
  закреплённым сертификатом, это должен быть следующий ADR.

## Работа на стороне сервера (для сессии репозитория VPN)

1. **Поле манифеста.** Инструмент выпуска (`deploy.exe app-release`)
   записывает `control_planes` в манифест из текущего адреса control plane
   до подписи. Он должен отказывать в адресах из loopback, частных и
   документационных диапазонов.
2. **Повторная публикация без новой версии.** Способ заново подписать и
   опубликовать манифест текущей версии с новым `released_at` и новым
   `control_planes` во все каналы (control plane, зеркала, ассеты выпуска
   на хостинге кода), не собирая новый установщик.
3. **Напоминание при переезде.** `deploy.exe migrate` в конце печатает
   команду из пункта 2.
4. **Control plane отдаёт поле.** `/api/v1/app/update` и `.sig` отдают
   заново опубликованный манифест байт в байт (так уже есть, если он
   отдаёт сохранённый файл).
5. Необязательно для этого ADR: TLS для API control plane, он понадобится
   следующему ADR.
